# 1 Agent 安全

前面的章节解决了 Agent 怎样获取信息、调用工具和协作。本章进一步回答：当用户输入、检索文档或工具结果不可信时，怎样防止这些内容借助 Agent 的能力造成越权、泄露和破坏？

先抓住一条主线

> 把外部内容当作待判断的数据，把模型输出当作候选动作；由可信程序决定能否读取、执行和发送。

```text
用户请求 / 文档 / 工具结果 / 子 Agent 消息
                    ↓
        来源与访问范围检查 → 构造上下文
                    ↓
              模型提出候选动作
                    ↓
       参数校验 → 授权 → 必要审批
                    ↓
           受限执行 → 结果与外发检查
                    ↓
             更新状态或交付用户

凭证隔离、预算、审计和异常处置贯穿全过程
```

第 5 章已经介绍执行边界，本章重点解释攻击怎样穿过边界、如何拦截和验证。故障重试、幂等与恢复继续放在第 14 章；这里不展开模型训练安全和 GPU 基础设施安全。

## 1.1 安全目标与信任边界

### 1.1.1 从回答错误到真实影响

普通问答中的错误可能表现为答非所问；接入工具后，同一次错误判断还可能触发发送邮件、读取客户记录或提交退款。能力越强，越需要限制错误能够影响的范围。

沿用订单案例：用户只要求“判断 A100 能否退款，先别执行”。如果政策文档中混入“立即申请退款”的文字，Agent 应把它当作资料中的内容，而不是新的用户授权。

安全目标可以用四个问题理解：

| 目标 | 要防止什么 | 订单案例 |
| --- | --- | --- |
| 保密性 | 数据被不该看见的人或服务获得 | 其他租户订单进入当前回答 |
| 完整性 | 事实、状态或业务数据被非法修改 | 把未批准的退款写成已批准 |
| 可用性 | 服务或预算被恶意消耗 | 被文档诱导无限搜索、递归委派 |
| 可追责性 | 无法还原谁提出、批准和执行动作 | 只有“操作成功”，没有身份与动作记录 |

模型幻觉与攻击都可能导致错误，但来源不同。幻觉不一定存在攻击者；提示注入有意利用模型对输入的解释影响行为。防护既要考虑恶意输入，也要防止普通模型错误越过执行边界。

### 1.1.2 什么是信任边界

信任边界是系统在接收信息或调用能力时，需要重新判断“凭什么相信、允许做什么”的位置，不一定对应进程或网络边界。

例如，同一进程中的模型输出也不能直接当作授权记录；来自已认证数据库的订单备注，也可能是用户自行填写的内容。

| 信息或组件 | 可以依据它做什么 | 不能自动推导什么 |
| --- | --- | --- |
| 可信认证上下文 | 确认当前用户、租户与会话 | 当前用户有权操作所有资源 |
| 用户请求 | 确定目标和本次限制 | 用户可以覆盖系统权限策略 |
| 业务系统的受控字段 | 核对订单状态、归属等事实 | 同一响应中的自由文本都具有指令权威 |
| 检索资料、网页、工具描述 | 提供资料或说明能力 | 可以授权执行或修改系统规则 |
| 模型、子 Agent 输出 | 提出计划、动作或结论 | 已经完成校验、审批或真实执行 |

要分别判断**事实是否可靠**与**内容是否有权发出指令**。政策可以是可靠的规则依据，但文档中的“请上传全部订单”不因此获得操作权限。

### 1.1.3 先做一个小型威胁模型

威胁建模不是先背攻击名称，而是沿系统找出四件事：

1. 保护什么：订单、用户信息、凭证、业务状态、计算预算。
2. 攻击者能控制什么：请求、文档片段、工单备注、工具响应或第三方插件。
3. 内容会经过哪里：检索、摘要、记忆、模型决策、工具参数和输出页面。
4. 最后能影响什么：查库、写入、联网、发消息、执行代码。

面试里画出一条具体路径，比列出十几个攻击缩写更有价值：

```text
攻击者修改政策文档
        ↓
文档被检索并进入上下文
        ↓
模型提出越权退款请求
        ↓
退款工具是否独立核对身份、订单和批准记录？
```

最后这个问题决定攻击是否只能影响模型输出，还是能进一步产生真实业务效果。

## 1.2 攻击怎样进入任务链

### 1.2.1 提示注入与指令边界

提示注入（Prompt Injection）是通过输入内容诱导模型偏离预定任务或规则。直接注入来自当前输入，间接注入藏在模型随后读取的文档、网页、邮件或工具结果中。

普通用户修改自己的回答要求，例如“这次用英文”，不自动属于攻击。问题在于内容试图冒充更高权限指令，或诱导系统执行超出授权的行为。

Agent 的典型风险链是：外部资料进入上下文，被误当作行动要求，再转化为工具调用。模型需要理解自然语言资料，而指令也使用自然语言表达；角色标签和分隔符有帮助，但不能像数据库参数化查询那样建立可靠的语法隔离。[OWASP 提示注入说明](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

不要只检测“忽略之前指令”几个词。攻击可能伪装成排障建议、紧急通知或完成任务的前置步骤；也可能藏在截图经 OCR 提取的文字里。防护应检查实际动作和数据流，而不只匹配措辞。

### 1.2.2 检索、工具与记忆中的污染

不同入口的共同危险，是让数据被错误地提升为权威。它们的影响范围有所不同：

| 入口 | 可能发生什么 | 主要防护位置 |
| --- | --- | --- |
| RAG 文档 | 错误条款影响结论，或嵌入命令诱导动作 | 入库来源、版本、检索权限与证据核验 |
| 工具描述 | 描述诱导调用无关工具或索取额外数据 | 工具注册、版本审核、能力范围 |
| 工具结果 | 返回内容声称“用户已经批准” | 结果按数据处理，审批记录独立查询 |
| 长期记忆 | 一次恶意内容被保存，反复影响后续任务 | 写入筛选、来源记录、撤销与过期 |
| 子 Agent 消息 | 局部结论被主 Agent 当作授权或已完成动作 | 委派契约、结果验证、权限传播 |

RAG 数据投毒不一定包含指令。例如把退款时限从 7 天改成 70 天，也能使答案错误。这属于知识完整性问题；仅检测提示注入无法解决，还要验证资料来源和适用版本。

摘要也不会自动消毒。如果摘要器把文档中的“建议跳过审批”改写为“已经批准”，反而会丢失原始来源和不确定性。进入长期记忆或控制状态前，应额外核验。

### 1.2.3 混淆代理与能力组合

混淆代理（Confused Deputy）是有权限的组件，被诱导替无权限的请求方执行操作。Agent 服务持有业务凭证，如果只检查“自己能不能调用”，却不检查“当前用户能不能操作这个订单”，就可能成为混淆代理。

```text
用户只允许读取自己的订单
        ↓
模型提出读取其他用户订单
        ↓
工具使用服务级凭证，数据库查询成功
        ↓
如果缺少资源归属校验 → 发生越权
```

单个工具安全，也不代表组合安全。读取内部资料本来合法，向外发邮件也可能合法；把读取结果发给不被允许的收件人，就产生数据外传。因此权限要同时考虑数据、动作和目的地。

MCP 统一的是接入方式，不会自动消除这种风险。客户端到 MCP Server、Server 到下游 API，应各自正确验证身份和令牌适用对象，不能把收到的令牌不加验证地透传。[MCP 安全实践](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

## 1.3 把执行权留在可信程序中

### 1.3.1 认证、授权与最小权限

认证回答“你是谁”，授权回答“你能对哪个对象做什么”。登录成功只是授权检查的输入，不是最终结论。

一个工具请求至少要结合以下信息判断：

```text
主体：当前用户、租户、被委派身份
动作：读取订单 / 申请退款 / 导出资料
资源：哪个订单、文档或接收方
条件：当前状态、金额、时间、本次任务范围
```

主体由可信认证链提供；工具名称和业务参数可以来自模型，但必须校验。不能接受模型传入的 `role="admin"` 或 `tenant_id` 来改变服务端身份。

最小权限不是“给所有 Agent 一个只读管理员账号”，而是只开放完成当前任务所需的动作与资源。默认拒绝，并在实际访问时检查权限，而不只在页面入口或工具列表中检查。[OWASP 授权实践](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### 1.3.2 工具可见性不等于执行授权

向模型隐藏写入工具，可以减少误调用，但不能作为唯一防线。模型可能输出旧工具名，其他客户端也可能直接调用后端接口。

有效控制应覆盖实际执行路径：

- 工具注册表只映射明确允许的实现，不按字符串动态执行任意函数。
- 工具执行层检查当前任务允许的动作，参数采用明确类型和范围。
- 业务服务核对资源归属、当前业务状态和操作权限。
- 数据访问层按租户和对象范围取数据，不先读取全部记录再让模型筛选。

多 Agent 委派也不能默认扩大权限。子任务有效权限应受用户授权、父任务范围和子任务职责共同约束；政策专家没有写入权限，不能通过请求另一个专家间接获得。

### 1.3.3 审批绑定的是具体动作

授权说明用户是否有权，审批说明用户或审核者是否同意本次具体操作。用户有退款权限，但说了“先别执行”，系统就不应把一般权限当作本次同意。

```text
生成待执行动作
   ↓
向有权审批的人展示：对象、金额、收件人或修改差异
   ↓
保存审批记录：审批人、动作内容、任务、有效期
   ↓
执行前核对：当前请求是否仍与批准内容一致？权限是否仍有效？
   ├─ 不一致 → 拒绝，必要时重新审批
   └─ 一致 → 在业务服务中再次检查并执行
```

“是否继续？”不是充分的审批界面。用户应看见真正将发生的变更，而不是只看模型可能出错的总结。批准 100 元后参数改成 1000 元，必须重新确认。[OWASP 交易授权实践](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

审批后到执行前，权限、资源状态仍可能变化。这类“检查时成立，使用时已变化”的问题称为 TOCTOU（检查与使用之间的时间差）。执行前重查能缩小风险，但不能凭一次重查消除并发窗口；关键业务条件还要在事务、版本条件更新或服务端原子接口中保证。

审批记录不是幂等机制。相同动作通过审批后被提交两次，仍可能产生重复效果；需要第 5、14 章的业务操作 ID、幂等与结果核对。

### 1.3.4 Guardrail 的作用与局限

Guardrail（护栏）是对输入、输出或动作进行检查的机制，可以由规则、分类模型或其他检测服务实现，不特指某个框架 API。

| 检查方式 | 擅长的问题 | 不能替代什么 |
| --- | --- | --- |
| 确定性规则 | 类型、金额范围、资源归属、域名限制 | 任意自然语言意图判断 |
| 模型检测 | 可疑指令、上下文相关风险、语义异常 | 服务端授权和业务一致性 |
| 人工复核 | 高影响、不可逆或难自动判断的操作 | 清晰的动作展示与身份校验 |

组合原则是：能用可信数据和明确规则判断的，不交给模型投票；模型检测用于补充语义判断。检测器自身也可能误判或受输入影响，不能宣称“再加一个安全 Agent 就安全了”。

高风险写入所必需的授权或审批检查不可用时，应暂停执行，而不是自动放行。低风险任务可以降级为解释、草稿或人工处理。风险分级有助于避免所有动作都反复弹窗，减少审批疲劳。

## 1.4 限制数据与工具的影响范围

### 1.4.1 从读取到输出都要控制数据

数据泄露不只发生在最终回答。敏感内容还可能出现在模型请求、外部重排服务、工具参数、日志、追踪平台和浏览器加载的链接中。

```text
原始资料 → 检索/重排 → 模型输入 → 工具或页面输出
             │           │             │
          可见范围     必要字段      接收方与目的地
```

对企业 RAG，应在资料暴露给重排器或模型之前落实访问控制；不能先把所有租户内容送给模型，再要求它“不提及其他租户”。正文、摘要、向量索引和缓存也应遵守相同的数据范围。

需要同时处理三个问题：

- **数据最小化**：判断退款通常不需要完整地址或支付凭证，只传必要字段。
- **缓存与撤权**：缓存键区分必要的租户和权限范围；权限改变后，不能仅凭旧缓存命中继续返回。
- **输出接收方**：有权读取不等于有权发送给任意邮箱、网址或第三方模型服务。

凭证应由执行层按需取得，不放进工具描述、系统提示词或普通日志。隐藏 system prompt 不能充当密钥保护方案；即使提示词被获知，资源访问仍应有独立权限控制。

页面渲染也要谨慎：生成的 HTML、Markdown 链接或远程图片可能触发浏览器请求。是否允许自动加载外部资源，应由渲染策略决定，不能只检查回答正文有没有敏感词。

### 1.4.2 工具仍然面对传统注入风险

模型生成的参数，本质上也是外部输入。Agent 安全不会替代后端安全：

| 工具类型 | 典型风险 | 设计方向 |
| --- | --- | --- |
| SQL 查询 | 拼接参数改变查询语义 | 参数化值、允许的表与字段、只读或受限账号 |
| 命令执行 | 字符串被 Shell 解释为额外命令 | 固定程序、独立参数、参数白名单，避免不必要的 Shell |
| 文件读写 | 路径穿越或符号链接访问范围外文件 | 受控根目录、路径与链接策略、操作系统级隔离 |
| URL 获取 | 服务端请求伪造，访问内部资源 | 目标范围限制、地址验证与出站网络策略 |

参数化 SQL 主要保护值参数；动态表名和排序字段通常还需映射到白名单。关闭 Shell 也不意味着任意程序参数都安全，某些参数本身就能读取文件或联网。

SSRF（服务端请求伪造）的核心是：攻击者借服务端的网络位置访问本不该访问的目标。一个“帮我读取这个网址”的工具，可能拥有浏览器用户没有的内网访问能力。

不能只判断 URL 字符串是否以可信域名开头。解析、重定向、IPv4/IPv6 地址以及域名实际解析结果都可能影响目标；检查结果还必须与真实连接一致，避免检查后重新解析绕开限制。出站代理或网络策略可以提供另一层限制。[OWASP SSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

### 1.4.3 沙箱、依赖与预算

沙箱限制代码能够接触的文件、网络、进程和资源。它主要降低失控后的影响范围，不负责判断订单是否属于当前用户。

执行环境可以按任务限制：

- 不挂载不必要的宿主目录、凭证或管理接口。
- 以低权限身份运行，只开放所需文件路径和网络目的地。
- 限制 CPU、内存、执行时间、进程数量和输出体积。
- 区分临时工作区和正式数据，任务结束后按策略清理。

容器并不自动等于强隔离沙箱。特权运行、敏感挂载和开放网络都可能削弱边界；隔离强度要按执行代码的可信程度选择。

工具、Skill、MCP Server 和依赖包也是供应链的一部分。新增或升级能力时，应检查来源、版本、请求权限和行为变化。注册表中能发现某个工具，不代表它值得信任；给已知 Server 换一个有更大权限的新版本，也应重新评估。

预算同样是安全边界：限制总轮数、调用数量、委派深度和并发，防止外部内容诱导无限处理。不能只限制单次请求，而忽略多个子任务合计消耗。[OWASP Agent 安全工程建议](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

## 1.5 一个可运行的动作检查示例

### 1.5.1 用代码看清授权与审批

下面用 Python 3.9+ 标准库模拟退款动作的检查。模型只能提交动作参数；身份、订单和批准记录由可信服务提供。示例不调用模型、不联网，也不执行退款。

```python
from dataclasses import dataclass, replace


@dataclass(frozen=True)
class Context:
    user_id: str
    tenant_id: str
    task_id: str
    scopes: frozenset


@dataclass(frozen=True)
class Order:
    order_id: str
    user_id: str
    tenant_id: str
    refundable_cents: int


@dataclass(frozen=True)
class Approval:
    user_id: str
    tenant_id: str
    task_id: str
    order_id: str
    amount_cents: int
    expires_at: int


def check_refund(ctx, request, order, approval, now):
    # request 不可信；其余参数在真实系统中来自可信服务。
    required = {"tool", "order_id", "amount_cents"}
    if not isinstance(request, dict) or set(request) != required:
        return "INVALID_REQUEST"
    if request["tool"] != "request_refund":
        return "UNKNOWN_TOOL"
    amount = request["amount_cents"]
    if (not isinstance(request["order_id"], str)
            or type(amount) is not int or amount <= 0):
        return "INVALID_ARGUMENTS"
    if "refund:submit" not in ctx.scopes:
        return "FORBIDDEN"
    if (order is None or order.order_id != request["order_id"]
            or order.user_id != ctx.user_id
            or order.tenant_id != ctx.tenant_id):
        return "FORBIDDEN"
    if amount > order.refundable_cents:
        return "BUSINESS_DENIED"
    if approval is None:
        return "APPROVAL_REQUIRED"
    expected = (ctx.user_id, ctx.tenant_id, ctx.task_id,
                order.order_id, amount)
    approved = (approval.user_id, approval.tenant_id, approval.task_id,
                approval.order_id, approval.amount_cents)
    if approved != expected or now >= approval.expires_at:
        return "APPROVAL_INVALID"
    return "ALLOWED_FOR_NEXT_CHECK"


if __name__ == "__main__":
    ctx = Context("u1", "t1", "task-1", frozenset({"refund:submit"}))
    order = Order("A100", "u1", "t1", 10000)
    approval = Approval("u1", "t1", "task-1", "A100", 1000, 2000)
    request = {"tool": "request_refund", "order_id": "A100",
               "amount_cents": 1000}
    assert check_refund(ctx, request, order, approval, 1000) == "ALLOWED_FOR_NEXT_CHECK"
    assert check_refund(ctx, request, order, None, 1000) == "APPROVAL_REQUIRED"
    changed = dict(request, amount_cents=2000)
    assert check_refund(ctx, changed, order, approval, 1000) == "APPROVAL_INVALID"
    other = replace(ctx, tenant_id="t2")
    assert check_refund(other, request, order, approval, 1000) == "FORBIDDEN"
    assert check_refund(ctx, request, order, approval, 2000) == "APPROVAL_INVALID"
    print("5 checks passed; no refund executed")
```

### 1.5.2 关键语句与设计思想

按执行顺序理解：

1. `Context` 保存可信身份和任务范围；不能直接用模型提交的字典构造它。`frozen=True` 只防止普通字段赋值，不提供认证或防伪能力。
2. `set(request) != required` 拒绝未约定字段，例如模型添加 `approved=True`，不能因此绕过审批。
3. `type(amount) is not int` 在本例中也拒绝 Python 的布尔值，避免 `True` 被当作整数金额；金额统一使用分。
4. `ctx.scopes` 检查动作权限；订单的用户和租户检查资源范围，两者缺一不可。
5. `refundable_cents` 表达一个简化业务条件，不把“有权操作”误当作“任何金额都合法”。
6. `expected` 与 `approved` 对比本次任务、对象和金额，防止更换参数后复用旧批准。
7. `now >= expires_at` 拒绝过期批准；真实时间应来自可信执行环境，不能由模型选择。
8. `ALLOWED_FOR_NEXT_CHECK` 表示通过当前检查，不表示退款已执行，也不表示可以跳过业务服务的最终检查。

这里故意不检测提示词中有没有“忽略规则”。即使模型已经产生危险请求，程序仍应依据身份、资源和批准记录拒绝它。这是动作边界与模型行为检测的区别。

### 1.5.3 示例没有保障什么

本例只演示单次检查，不是生产审批系统。还缺少：

- 真实认证、审批人的权限验证、批准记录的可信存储与撤销。
- 执行时的完整退款规则、并发状态更新和服务端原子检查。
- 审批使用状态、业务幂等键、动作执行记录和失败恢复。
- 日志脱敏、接口限流以及工具实现的执行隔离。

示例的 `Approval` 专用于退款，因此没有通用动作类型字段；设计通用审批表时，还应绑定工具、动作类型、参数版本等。批准字段齐全也不代表记录真实，记录必须来自可信审批流程。

## 1.6 怎样验证系统真的安全

### 1.6.1 同时测试模型与执行边界

只向聊天框输入一次恶意请求，看模型是否拒绝，覆盖不了整个系统。至少需要两组测试：

- **模型行为测试**：给模型不可信材料，观察它是否提出危险调用、丢失约束或泄露内容。
- **系统边界测试**：绕过模型，直接向工具或业务接口提交不合法请求，确认程序仍会拒绝。

第二组尤其重要：模型暂时没有产生某个错误，不意味着后端能够阻止这个错误。

测试应使用合成订单、测试租户、模拟收件箱与受控工具，不能为了验证防线，把真实敏感数据发送到外部地址。

| 测试场景 | 预期观察 |
| --- | --- |
| 政策文档声称可以跳过审批 | 没有批准记录就不能执行退款 |
| 工具结果声称用户已批准 | 不更新可信审批状态，不自动放行 |
| 用户请求其他租户订单 | 不向模型返回内容，不泄露对象存在性等不必要信息 |
| 批准后修改金额、收件人或任务 ID | 旧批准失效，不能执行变更后的动作 |
| 等待审批时用户权限被撤销 | 恢复后重新授权，不能复用旧许可 |
| 文档已撤权，但旧摘要或缓存还存在 | 当前请求无法通过这些副本取得资料 |
| URL 跳转到不允许的地址 | 网络请求被阻止，而非事后只隐藏回答 |
| 主 Agent 委派无权限写入 | 子 Agent 和实际工具均不能扩大权限 |
| 安全检查服务不可用 | 必需检查未完成时，高风险写入暂停 |

### 1.6.2 拒绝率不等于安全效果

要区分三种结果：

```text
模型拒绝危险要求              → 行为层拦截
模型提出危险动作，工具拒绝执行 → 系统边界生效
模型说“不能操作”，后台却执行了 → 系统仍不安全
```

测试指标可以按层记录：

- 危险调用提出率：攻击样本中，模型提出不允许动作的比例。
- 越权或泄露成功率：攻击是否真正造成禁止的业务效果或数据暴露。
- 正常任务误拦率：合法任务被错误拒绝的比例。
- 合法任务完成率、额外时延和人工复核量：观察防护代价。

每个指标都要说明分母、攻击类型和成功判定。只报告“拦截了 99%”而不说明是文本拒绝还是实际执行拦截，无法判断系统边界。

有限测试中没有发现漏洞，不等于证明安全。模型、提示词、工具描述和权限逻辑升级后，都应对关键场景回归；多轮攻击还要覆盖前后文组合，而不只是单条输入。

### 1.6.3 审计与异常处置

日志应能还原：谁发起任务、模型提出什么动作、哪条策略允许或拒绝、谁批准、最后是否执行成功。

建议关联任务 ID、调用 ID、业务操作 ID、主体、资源、参数摘要、策略版本和审批记录。三种 ID 分别追踪任务、交互和业务效果，不能只用一个日志行号代替。

审计不等于保存所有原文。凭证、完整客户资料和不必要的工具结果应脱敏或避免记录，审计日志本身也要控制访问和保留范围。

发现异常后，先限制继续影响：暂停高风险工具、撤销相关授权或凭证、隔离污染资料与记忆，再核对已经发生的操作并保留证据。停止 Agent 不会自动撤回已发送的邮件或已执行的退款。

## 1.7 常见误区

| 误区 | 正确认识 |
| --- | --- |
| 写好 system prompt 就建立了权限边界 | 提示词指导行为，授权必须在可信程序中执行 |
| 用户登录了，就可以调用所有工具 | 还要检查动作、资源、租户和当前任务范围 |
| 内部工具返回的内容都可信 | 返回中的用户文本仍可能恶意，事实来源也不等于指令权威 |
| 只读 Agent 没有安全风险 | 仍可能泄露数据、外传资料或耗尽预算 |
| Tool Schema 严格就能防止注入 | 格式合法不代表参数安全、动作有权或内容真实 |
| 批准一次就能随意继续执行 | 批准应绑定具体动作，变更、过期与撤权都需处理 |
| 多加一个审核模型就足够 | 审核模型也会误判，不能代替资源授权与执行隔离 |
| 容器或 MCP 自动提供完整安全性 | 它们分别提供运行或接入能力，配置和业务权限仍由系统负责 |
| 模型拒绝率高就代表系统安全 | 必须观察实际工具执行、数据流和业务效果 |

## 1.8 面试高频问题

### 1.8.1 为什么 Agent 比普通问答更需要安全设计？

**参考回答**

Agent 把模型输出连接到了读取、写入、联网和代码执行能力。错误不再只停留在文本里，可能通过工具变成真实业务效果；多轮调用、记忆和委派还会扩大传播范围。

因此要把模型输出视为候选动作，独立验证身份、资源范围和本次授权，并限制执行环境、数据外发和任务预算。

**面试官追问**

- 只读工具可以放松控制吗：可以按风险减少审批，但不能省略读取权限和输出接收方检查；数据泄露不需要写入。
- 是不是模型越强越安全：模型能力可能改善判断，但不能替代凭证隔离、服务端授权和业务一致性。

**容易答错的地方**

- 把安全全部解释为过滤有害回答。
- 只讨论模型表现，不讨论实际工具权限和数据流。

### 1.8.2 如何防御间接提示注入？

**参考回答**

先限制外部材料的可见范围，保留来源，避免把资料拼接成高权限指令；再通过输入、输出和动作检查发现异常。关键防线是：即使模型受到影响，工具仍依据可信身份、任务范围和审批记录决定能否执行。

还要限制外发目的地和执行环境，防止读取与发送工具组合造成泄露。没有一段通用提示词可以保证拦住所有间接注入。

**面试官追问**

- 给文档加标签够不够：能帮助区分资料，但不是权限控制，必须配合实际执行检查。
- 先用另一个模型清洗文档呢：可以辅助检测，但可能遗漏或把恶意指令改写得更像事实；来源与确定性边界仍需保留。

**容易答错的地方**

- 只匹配“忽略之前规则”等关键词。
- 把经过摘要或来自内部系统的内容一律当作可信指令。

### 1.8.3 工具怎样避免成为混淆代理？

**参考回答**

不能只验证工具服务自己是否有凭证，而应核对当前主体对目标资源和动作的权限。用户、租户和任务范围来自可信认证与委派链，不能由模型随意填写。

业务服务即使使用服务级凭证访问数据库，也必须限制到本次请求允许的数据和动作；子 Agent 或 MCP 转发不能默认获得更大权限。

**面试官追问**

- 把 `user_id` 从 Schema 中删除就够了吗：不够，还要从可信上下文取得身份，并真正用于业务查询和执行校验。
- 缓存如何处理：缓存需要区分影响可见结果的身份与权限范围，撤权后不能继续命中并返回旧内容。

**容易答错的地方**

- 认为工具拿着合法 API Key，就代表当前用户合法。
- 只做工具级授权，不做对象级和租户级授权。

### 1.8.4 如何设计可靠的人工审批？

**参考回答**

让有权审批的人看见具体对象、金额、收件人或修改差异，把批准绑定到任务和实际动作，并设置有效期。执行前核对参数、权限和业务状态；参数变化需要重新审批。

审批本身不提供幂等或事务保障。业务执行还需要处理重复提交与并发条件，不能把“用户点过确认”当作所有后续检查的替代品。

**面试官追问**

- 模型说用户已经批准怎么办：查询可信审批记录，不从模型文本恢复授权事实。
- 所有工具都审批是否最好：可能造成疲劳和误点，应按风险分级，把复核集中到高影响动作，同时保留低风险动作的自动授权检查。

**容易答错的地方**

- 用 `approved=True` 作为可由模型传入的普通参数。
- 把一次批准当成永久权限或防重复执行机制。

### 1.8.5 有沙箱和 Guardrail，为什么还要业务权限检查？

**参考回答**

沙箱限制工具能接触哪些资源，Guardrail 检查内容或动作风险，业务授权判断当前用户能否对具体对象操作。三者解决的问题不同。

即使工具被限制在某个业务 API 内，仍可能用有效凭证读取另一个租户的数据；即使内容检测认为请求正常，也不能证明用户拥有该订单。

**面试官追问**

- 安全检查超时要不要放行：高风险操作不能在必需检查未完成时放行，可以暂停或转人工；低风险任务按明确策略降级。
- URL 工具怎么限制：结合解析后的目标、实际连接地址、重定向和出站网络策略，不能只检查字符串前缀。

**容易答错的地方**

- 把容器当作自动安全的环境。
- 用语义分类代替确定的身份与资源授权。

### 1.8.6 怎样证明 Agent 的防护有效？

**参考回答**

按威胁模型构造攻击样本与正常样本，分别测试模型行为和执行边界。直接提交恶意工具请求，验证后端拒绝；再通过不可信文档、工具结果、多轮上下文和委派链做端到端测试。

指标同时观察实际越权或泄露、正常任务误拦、任务完成率与成本。测试通过只能说明覆盖范围内没有发现对应问题，不能证明系统绝对安全。

**面试官追问**

- 模型被诱导调用退款，但工具拒绝了算什么：模型行为层存在问题，执行防线在该案例中有效，两者分别记录。
- 如何避免测试造成真实泄露：使用合成数据、测试账号和受控输出端，以调用记录和模拟业务状态判断影响。

**容易答错的地方**

- 只展示几条模型拒绝截图。
- 不定义攻击成功条件，也不检查真实业务效果。

面试中用一个场景串起来：谁能控制输入 → 内容经过哪些组件 → 可能提出什么危险动作 → 哪一层依据什么拒绝 → 如何验证没有产生副作用。

核心不是让模型承诺不犯错，而是让系统在模型可能犯错时，仍有明确、可测试的权限和影响范围。
