# 1 可靠性与恢复

前面的章节已经让 Agent 能调用工具、保存状态和等待审批。但任务可能持续几分钟甚至几天，期间模型会超时、Worker 会重启、消息会重复，外部动作还可能已经成功却没有回传结果。

本章要解决的不是“如何保证永远不出错”，而是：出错后，系统怎样知道真实进度，怎样安全继续，以及什么时候必须停止自动处理。

先抓住一条主线

> 先记录可恢复的任务与动作，再执行；失败后先核对事实，再决定重试、继续、补偿或转人工。

```text
任务持久化 → 调度与领取 → 执行模型或工具 → 保存结果与进度
                  ↑                          │
                  │        中断或失败         ↓
                  └── 可安全继续 ← 核对本地状态与外部动作
                                      ├─ 暂时故障 → 有限重试
                                      ├─ 等待条件 → 暂停
                                      └─ 无法确认 → 对账 / 人工处理
```

第 5 章讲 Harness 的职责，第 10 章讲 LangGraph 的检查点与节点重入。本章把它们放进持久化任务、并发 Worker 和外部业务服务中，重点解释恢复为何不能只靠一个 Checkpoint。

## 1.1 从故障时间线理解可靠性

### 1.1.1 可靠性不只是接口返回成功

对 Agent 任务，可靠性至少包含三个要求：

- **不丢任务**：系统已确认接收的任务，不能因为进程重启就消失。
- **不重复产生危险效果**：重复消息或恢复重放，不能变成重复退款、重复发货。
- **如实报告状态**：不知道是否成功时标记未知，未完成时不能伪装完成。

它还要求任务在可满足的条件下继续推进，而不是永远卡在“运行中”。授权已撤销、证据始终缺失或外部结果不可确认时，可靠行为可能是暂停并给出可处理的原因。

可靠性不等于答案质量。一个执行流程可以稳定地完成，但模型结论仍可能不准确；完整系统还需要第 16 章的任务质量评测。

### 1.1.2 成功、失败与结果未知

沿用订单退款案例，观察三个不同时间点：

```text
T1：Worker 发出申请退款请求
T2：退款服务已提交业务事务
T3：Worker 收到成功响应并保存动作结果

在 T1 前失败：可能尚未发出请求，要依据发送记录判断
在 T1 与 T2 之间中断：调用方通常不能确定服务是否执行
在 T2 与 T3 之间中断：业务已成功，但本地可能仍显示执行中
```

超时表示“在等待期限内没有取得结果”，不等于“服务没有执行”。HTTP 5xx、连接中断也不能单凭错误类别证明没有副作用，具体要看服务契约和查询结果。

| 动作状态 | 已知事实 | 接下来做什么 |
| --- | --- | --- |
| 成功 | 获得可靠的业务结果或查询确认 | 记录结果，推进依赖步骤 |
| 明确失败 | 服务明确拒绝，且契约说明未产生目标效果 | 修正条件、结束或按策略重试 |
| 执行中 | 服务已受理，尚未到终态 | 按业务操作 ID 查询，不重复创建新操作 |
| 结果未知 | 请求可能产生效果，但本地无法确认 | 对账、幂等重试或人工核对 |

这里的“动作状态”不等于整个任务状态。查询订单成功，只能说明这一步完成；政策查询失败时，任务仍可能处于部分完成。

### 1.1.3 执行语义必须说明范围

At-most-once、at-least-once、exactly-once 常被翻译为至多一次、至少一次和恰好一次，但面试时首先要问：指消息交付、处理尝试，还是最终业务效果？

| 语义 | 可以怎样理解 | 主要代价或边界 |
| --- | --- | --- |
| At-most-once | 在指定环节最多处理一次，可能不重试 | 故障时可能漏处理或保留未知结果 |
| At-least-once | 为避免遗漏允许再次交付或处理 | 消费方必须考虑重复 |
| Exactly-once | 在声明的事务或处理边界内，效果恰好一次 | 不能自动延伸到任意外部 API |

实际任务系统常采用“允许重复投递 + 幂等业务操作”。它让多次尝试对应同一个逻辑效果，但仍依赖服务契约、去重记录和恢复流程，不是网络层突然保证只发出一次请求。

有限重试也不是“每个任务最终都一定成功”：依赖长期不可用或参数永久错误时，系统应把任务送到可检查、可恢复的失败状态。

## 1.2 重试与业务幂等

### 1.2.1 先分类，再决定是否重试

重试适用于“条件可能暂时不满足，且再次尝试不会造成不可接受的重复效果”。不是所有异常都符合这两个条件。

| 情况 | 优先处理方式 |
| --- | --- |
| 模型接口暂时不可用、依赖限流 | 在剩余预算内退避重试，遵守服务提供的等待指示 |
| 工具参数格式错误 | 修正参数或询问用户，不原样重复 |
| 业务条件不满足 | 解释原因、调整方案或结束 |
| 权限不足、审批过期 | 进入合法授权或审批流程，不能绕过 |
| 写入请求超时、效果未知 | 按操作 ID 核对；只在契约允许时做幂等重试 |

模型重试、工具重试和重新规划也不是一回事：

- 模型重试重新请求生成结果，可能增加费用、产生不同输出。
- 工具重试重新尝试同一业务动作，必须维护操作身份。
- 重新规划改变后续方案，不能把已经完成的写入当作没有发生。

工具 SDK 与运行时应约定谁负责重试，并共享总截止时间。否则外层重试三次、内层也三次，就可能把一次故障放大成九次请求。

### 1.2.2 截止时间、退避与抖动

Timeout（超时）限制某次等待；Deadline（截止时间）限制整项任务还能运行多久。每一步都重新获得完整超时时间，会让总耗时远超用户预期。

一种设计方式是：单次调用允许等待的时间，不超过“该调用配置的上限”和“任务剩余时间”中的较小者，并为记录结果、清理和交付预留余量。

指数退避让连续失败后的等待逐渐增加；随机抖动让多个 Worker 不在同一时刻一起重试。例如第 n 次重试可在下面的区间内随机选择等待时间：

```text
0 ≤ 等待时间 ≤ min(最大退避时间, 初始间隔 × 2^n)
```

它用于降低同步重试对依赖的冲击，不是所有场景的固定最佳参数。交互任务要兼顾等待体验，后台任务可以接受更长退避；重试仍受最大次数和总期限约束。

退避解决压力，幂等解决重复效果，二者不能互相替代。

### 1.2.3 幂等键与动作账本

第 5 章已经介绍幂等。本章进一步把它落实到任务数据：同一业务意图重试时，使用同一个 `operation_id`；每次尝试可以有不同的 `attempt_id`。

```text
task_id：本次“判断并按批准条件处理退款”的任务
   └─ operation_id：其中一次确定的退款申请
         ├─ attempt_id=1：响应丢失
         └─ attempt_id=2：查询或幂等重试，取得同一结果
```

不要每次恢复都重新生成操作 ID，也不能只拿订单号作为所有退款的去重键：同一订单可能存在不同的合法部分退款。键应绑定明确业务意图，作用域通常还需包含租户和动作类型。

动作账本可以保存以下信息：

- 操作 ID、任务 ID、动作类型、目标对象。
- 规范化后的参数或其摘要，防止同键换参数。
- 执行状态、尝试记录、外部业务 ID 与结果。
- 创建时间、最近核对时间，以及需要人工处理的原因。

同库操作可以用唯一约束和事务，把“登记去重结果”与“业务更新”一起提交。不能采用“先查没有，再无保护地执行”的方式：两个 Worker 可能同时查到没有记录。

去重记录的保留期也是契约的一部分。过早删除后，迟到的重试可能再次执行；需要明确重试窗口、长期业务唯一约束和归档策略。

### 1.2.4 跨服务操作与补偿

本地数据库事务无法自动覆盖远程退款服务。调用方即使先记录 `running`，也仍可能在“远端成功、本地未更新”时中断。

恢复时按下游能力处理：

1. 有稳定操作查询接口：查询外部结果，再修正本地记录。
2. 支持幂等键：在允许范围内以原键和原参数重试，获取既有结果或进度。
3. 两者都没有：不能承诺安全自动重放；结合业务流水核对，必要时转人工。

查询暂时返回“未找到”也未必说明请求未执行。索引或读副本可能延迟，需理解查询接口的一致性与最终状态语义。

补偿是在后续失败时发起一个新的业务动作，尽量抵消已完成步骤的影响。例如预留库存后支付失败，可以尝试释放预留。它不是数据库回滚，也不一定能恢复原状：邮件发出后无法让收件人“没看见”。

多个步骤及其补偿常称为 Saga 思路。补偿本身可能失败，也需要操作 ID、重试和人工兜底；外部结果仍未知时，不应未经核对就同时发起反向操作。

## 1.3 持久化任务与消息交付

### 1.3.1 任务寿命与请求连接分开

HTTP 连接可能几秒后断开，任务却需要等待审批几小时。将任务放进进程内后台协程，只解决“不阻塞请求”，不解决进程重启后的丢失。

一个常见执行框架是：

```text
客户端提交 → API 持久化任务 → 返回 task_id
                         ↓
                    队列或数据库调度
                         ↓
                  Worker 领取并执行
                         ↓
               更新状态、结果与动作记录

客户端通过 task_id 查询，或接收带序号的进度事件
```

只有达到接口约定的持久化边界，才能告诉用户“任务已接收”。提交响应丢失时，客户端可能再次提交，因此任务创建也可以使用客户端提交键去重，而不只对内部工具动作做幂等。

任务记录至少包括目标、约束、状态、进度引用、版本、截止时间，以及等待或失败原因。持久化承诺仍取决于数据库配置、备份和故障模型，不能把“调用了一次写入”当作绝对不丢失。

### 1.3.2 Outbox 解决数据库与队列的双写

若 API 先写任务表再发消息，中间崩溃会留下永远没有调度消息的任务；先发消息再写表，则 Worker 可能收到一个尚不存在的任务。

Transactional Outbox（事务发件箱）把任务记录和“需要发送的事件”放进同一个数据库事务：

```text
本地事务：写 Task + 写 Outbox → 一起提交
                                 ↓
后台投递器读取 Outbox → 发到队列 → 标记已投递
```

若发送成功后、标记之前崩溃，投递器会再次发送，所以消费方仍需处理重复。Outbox 保证已提交的发送意图可继续投递，不是数据库与消息队列完成了一次跨系统原子提交。[AWS Outbox 模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

简单系统也可以由 Worker 直接轮询任务表，避免引入第二套队列。是否采用消息中间件，应看吞吐、唤醒延迟和运维条件，而不是认为 Agent 必须配置完整分布式组件。

### 1.3.3 消息确认与失败收敛

ACK（确认）告诉队列这条消息可以按其语义结束本次交付。过早确认后 Worker 崩溃，可能丢任务；持久记录完成后再确认，则 ACK 丢失时可能再次投递。

常见选择是接受后者：重复消费时读取任务和动作记录，已完成则返回或确认，不重新执行。若提前 ACK，必须先把后续执行责任可靠地转移到另一个持久系统，而不是只放进内存。

持续失败的任务不能无限重入热队列。可保存下一次可重试时间，超过策略上限后转入失败队列或死信队列，保留原因供检查。

死信队列不是问题自动解决了。重新投递前要确认失败原因已处理，并复用原业务操作身份；否则“人工点重试”仍可能造成重复动作。

## 1.4 多 Worker 的执行协调

### 1.4.1 租约、心跳与任务领取

租约（Lease）表示某个 Worker 在一段时间内拥有任务的执行资格。Worker 领取任务后定期续约；长期没有续约，调度器允许其他 Worker 接手。

```text
短事务领取：ready → running
             保存 owner、lease_until、generation
                     ↓ 提交事务，释放数据库锁
长操作执行：模型、工具、外部服务调用；按需续约
                     ↓
短事务提交：校验 owner 与 generation → 更新进度
```

不能在等待模型的整个过程中持有数据库长事务和行锁。它们会占连接、阻塞其他更新，并增加故障后的清理负担。

领取必须是原子的条件更新，不能“先读取 ready，再无条件写 running”。数据库队列也可用 `FOR UPDATE SKIP LOCKED` 让不同消费者避开彼此正在领取的行；它适合队列式取任务，不适合作为需要完整一致视图的一般查询。[PostgreSQL 锁定查询说明](https://www.postgresql.org/docs/current/sql-select.html)

### 1.4.2 租约过期不代表旧 Worker 停止

这是最容易遗漏的恢复窗口：

```text
Worker A 领取 generation=7 → 网络阻塞，续约失败
租约到期
Worker B 接手 generation=8 → 开始恢复
Worker A 恢复运行          → 仍可能尝试提交旧结果
```

因此，提交状态时应校验当前拥有者、领取代次以及所需的租约条件。使用单调增加的 fencing token（隔离令牌）时，存储或被保护资源拒绝旧代次写入，才能限制过期执行者。

仅在任务表检查代次，不能阻止 A 已经向不支持该机制的外部 API 发请求。外部副作用仍要依赖幂等、业务版本校验或受控执行入口。

心跳只能表明 Worker 在回应，不能证明业务有进展。模型请求卡住但心跳线程正常时，任务仍可能永远运行；还应检查步骤超时、进度更新时间和总截止时间。

### 1.4.3 会话并发与共享资源冲突

同一个会话同时收到两条请求，两次运行可能都从旧状态出发，然后互相覆盖结果。解决方式取决于产品语义：按会话排队、取消或替换前一次请求，或者用状态版本进行乐观并发控制。

```text
读取 State version=12
       ↓
计算更新
       ↓
仅当 version 仍为 12 时提交，并更新为 13
       └─ 已变化 → 冲突处理，不能静默覆盖
```

重新读取状态后，不代表可以无条件重做外部动作。先检查旧尝试是否已经产生业务效果，再决定如何合并或继续。

会话级串行也不能解决全部业务冲突：两个不同会话可能同时操作同一订单。资源级一致性应由订单服务的事务、版本和业务约束保障；Reducer 合并状态不能替代这些能力。

## 1.5 从保存进度到安全恢复

### 1.5.1 恢复的正确顺序

恢复不是反序列化 State 后直接执行下一行。至少需要重新建立执行条件：

1. 读取任务、检查点和动作账本，确认没有被其他执行者接管或结束。
2. 核对状态 Schema、工作流和工具版本是否兼容，重建连接等运行资源。
3. 检查当前权限、批准范围、截止时间和取消请求。
4. 核对未知外部动作，避免用旧检查点覆盖已经发生的事实。
5. 判断已保存证据是否仍适用，再恢复最小必要步骤。

检查点描述程序进度，动作账本描述外部效果；冲突时应查业务事实，而不是让模型选择相信哪个文本。

LangGraph 等持久执行框架负责保存和恢复图状态，但外部动作应按其重放与持久化机制设计，不能从“有检查点”推出“工具不会重复执行”。具体框架接口已在第 10 章展开。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

### 1.5.2 版本变化与非确定性

旧任务可能保存 `amount`，新代码改成 `amount_cents`；工具同名但返回结构变化，也可能导致恢复错误。因此状态和工作流应有版本，升级时明确迁移、兼容运行或停止恢复的策略。

恢复也不保证产生与上次相同的模型输出。时间、随机数、检索结果、模型版本和业务状态都可能变化。

- 已确定的业务操作 ID、批准参数和外部业务 ID 应直接保留，不能重新生成。
- 已完成且仍有效的结果可以复用，不必为了恢复而再次调用模型。
- 实时状态可能需要重查；历史政策则应按适用时间和版本判断，不能随意换成最新版本。

节点按可恢复的业务步骤划分，通常比保存每个局部变量更清楚。检查点越频繁，可能减少重做成本，但增加存储与等待；关键外部动作仍需单独记录，不能靠提高保存频率消除不一致窗口。

### 1.5.3 暂停、取消与流式断连

等待审批是一种持久等待状态，不必占住 Worker 或不断轮询模型。批准事件到达后唤醒任务，重新检查批准和资源状态，再继续执行。

取消则是一项请求，不必然立即成为最终事实：

```text
用户请求取消 → 持久记录 cancel_requested
                      ↓
             停止派发新的步骤，通知运行中的步骤
                      ↓
             核对已发出的外部动作
                      ↓
       记录取消结果、已完成效果和仍待核对的动作
```

取消协程不等于取消远端操作。外部服务已受理退款时，本地停止等待也不会撤销退款；对用户应说明任务已停止继续执行，但某个已提交动作仍可能需要核对。

浏览器断开、事件流断开同样不等于业务取消。任务是否继续由接口约定决定；重连时先查询任务状态，再按事件序号补取进度，不能仅为了恢复界面而重新执行任务。

### 1.5.4 限制故障扩散

当模型服务变慢，盲目增加 Worker 和重试次数可能把局部故障放大。几种机制分别处理不同问题：

| 机制 | 主要作用 | Agent 场景 |
| --- | --- | --- |
| 限流 | 限制单位时间请求或并发 | 避免同时打满模型、工具配额 |
| 背压 | 下游积压时减慢上游接收或派发 | 队列堆积时减少新任务进入执行 |
| 熔断 | 依赖持续失败时暂时停止调用，再有限探测 | 避免对故障服务持续重试 |
| 降级 | 提供范围更小但真实的能力 | 只输出草稿、部分证据或转人工 |

队列和重试预算都应有上限。已接收任务无法在期限内完成时，应记录可解释的等待或失败，而不是无限堆积。

换备用模型属于一种降级，但要确认工具调用、结构化输出和任务约束兼容；不能以可用性为由取消必要审批，或把缺失证据包装成完整结果。

## 1.6 故障注入与可运行示例

### 1.6.1 模拟已提交但响应丢失

下面用 Python 3.9+ 标准库和临时 SQLite 文件，模拟一个简化业务服务：对订单增加“已退款金额”，同时保存操作结果。两项写入位于同一事务。

示例故意在提交后抛出超时，再关闭连接、重新打开数据库并用原操作 ID 重试。它不操作真实订单，也不连接外部服务。

```python
import os
import sqlite3
import tempfile


def refund(db, operation_id, amount_cents, lose_response=False):
    if not isinstance(operation_id, str) or not operation_id:
        raise ValueError("INVALID_OPERATION_ID")
    if type(amount_cents) is not int or amount_cents <= 0:
        raise ValueError("INVALID_AMOUNT")
    db.execute("BEGIN IMMEDIATE")
    try:
        old = db.execute(
            "SELECT amount, receipt FROM operations WHERE id = ?",
            (operation_id,),
        ).fetchone()
        if old is not None:
            if old[0] != amount_cents:
                raise ValueError("IDEMPOTENCY_KEY_REUSED")
            receipt = old[1]
        else:
            changed = db.execute(
                "UPDATE orders SET refunded = refunded + ? "
                "WHERE id = ? AND refunded + ? <= paid",
                (amount_cents, "A100", amount_cents),
            )
            if changed.rowcount != 1:
                raise ValueError("BUSINESS_DENIED")
            receipt = "refund:" + operation_id
            db.execute(
                "INSERT INTO operations(id, amount, receipt) VALUES (?, ?, ?)",
                (operation_id, amount_cents, receipt),
            )
        db.commit()
    except Exception:
        db.rollback()
        raise
    # 已提交之后丢失响应；此时 rollback 也不能撤销已提交事务。
    if lose_response:
        raise TimeoutError("RESPONSE_LOST_AFTER_COMMIT")
    return receipt


def main():
    with tempfile.TemporaryDirectory() as directory:
        path = os.path.join(directory, "demo.db")
        db = sqlite3.connect(path, isolation_level=None)
        try:
            db.executescript("""
                CREATE TABLE orders (
                    id TEXT PRIMARY KEY, paid INTEGER, refunded INTEGER
                );
                CREATE TABLE operations (
                    id TEXT PRIMARY KEY, amount INTEGER, receipt TEXT
                );
                INSERT INTO orders VALUES ('A100', 10000, 0);
            """)
            try:
                refund(db, "op-1", 1000, lose_response=True)
            except TimeoutError:
                print("调用方：结果未知，保留 op-1")
        finally:
            db.close()

        db = sqlite3.connect(path, isolation_level=None)
        try:
            receipt = refund(db, "op-1", 1000)
            assert receipt == "refund:op-1"
            assert db.execute("SELECT refunded FROM orders").fetchone()[0] == 1000
            assert db.execute("SELECT COUNT(*) FROM operations").fetchone()[0] == 1
            try:
                refund(db, "op-1", 2000)
            except ValueError as exc:
                assert str(exc) == "IDEMPOTENCY_KEY_REUSED"
            else:
                raise AssertionError("同键不同参数没有被拒绝")
            print("重试获得原结果；未重复退款；参数冲突被拒绝")
        finally:
            db.close()


if __name__ == "__main__":
    main()
```

### 1.6.2 关键语句与保证范围

按执行顺序理解：

1. `isolation_level=None` 配合显式 `BEGIN`、`commit` 和 `rollback` 管理事务，避免把隐式事务边界混入示例。
2. `BEGIN IMMEDIATE` 在 SQLite 中先取得写事务资格；本例不在数据库事务里执行网络调用。
3. `SELECT ... WHERE id = ?` 查询的是稳定业务操作 ID。找到旧结果就比较参数，不能把同键的新金额当成重试。
4. 条件 `UPDATE` 在业务更新时检查累计退款不超过已付金额，不采用无保护的“先读取余额再写入”。
5. `UPDATE` 与 `INSERT INTO operations` 在同一事务提交，因此本例业务效果和去重记录共同成功或回滚。
6. `TimeoutError` 位于提交之后，模拟“调用方没拿到结果，业务却已成功”的窗口。
7. 重新打开文件后用 `op-1` 重试，返回原凭据；最终金额仍为 1000，而不是 2000。

SQLite 接口与事务行为可参考 [Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)。这里使用兼容 Python 3.9 的显式事务写法，不要求新版本专有接口。

必须注意：本例把业务更新与操作记录放在**同一个 SQLite 数据库**。如果 `UPDATE` 换成远程支付调用，SQLite 事务不能撤销远程效果，也无法提供跨服务原子性。

本例也没有真实模拟进程被杀、电源故障、磁盘损坏或并发接管。它验证的是提交后超时、关闭重开连接和同键重试；真实生产还需要租户与对象范围、鉴权、审批、并发测试、存储耐久性及外部动作核对。

### 1.6.3 用故障矩阵验证恢复

不要只测正常成功，再加一个超时异常就认为完成恢复验证。应沿提交边界注入故障，并检查持久状态与业务效果：

| 注入位置或场景 | 恢复后应检查什么 |
| --- | --- |
| 任务提交成功，API 响应丢失 | 同一提交键不会新建重复任务 |
| Task 与 Outbox 事务提交后，投递器停止 | 恢复投递后任务能被调度 |
| 消息发送成功，投递标记未保存 | 重复消息不会重复业务效果 |
| 外部动作成功，本地动作记录未更新 | 使用原操作身份核对，不创建新动作 |
| Worker 租约过期后又恢复运行 | 旧代次无法覆盖新进度；外部重复请求可控制 |
| 两个会话同时操作同一订单 | 资源级约束仍然成立 |
| 审批等待后权限变化 | 恢复时重新授权，不沿用过期许可 |
| 取消与外部提交同时发生 | 状态如实记录已发生效果，不宣称全部撤销 |
| 存量任务读取新版本代码 | 能兼容、迁移或明确拒绝，不静默误解字段 |
| 依赖长时间故障 | 重试和队列有界，任务进入可处理状态 |

值得持续检查的不变量包括：同一操作 ID 不重复增加业务效果；成功任务都有可靠结果；失去执行资格的 Worker 不能提交新进度；未知动作不会直接变成成功或未执行。

恢复时间、重复尝试次数、长期未知动作数量和卡住任务数量可以帮助定位问题，但不能替代业务不变量。测试环境应使用模拟工具或受控业务数据，避免故障注入造成真实退款或外发。

## 1.7 常见误区

| 误区 | 正确认识 |
| --- | --- |
| 工具超时说明没有执行 | 超时只说明调用方没有及时取得结果 |
| 多重试几次就更可靠 | 可能放大压力、费用和重复副作用 |
| 每次重试换一个请求 ID 更安全 | 交互 ID 可以变化，业务操作 ID 应保持稳定 |
| 队列保证投递，任务就不会丢 | 还取决于任务持久化、确认时机和消费恢复 |
| 有 Checkpoint 就有 exactly-once | 检查点不自动覆盖外部业务效果 |
| 租约过期，旧 Worker 就不运行了 | 旧进程可能继续，需要防过期写入和业务幂等 |
| 在数据库事务里调用模型最保险 | 长时间占锁且不能自动让外部调用原子化 |
| 恢复旧状态可以撤销已经执行的动作 | 程序回放不等于现实业务回滚 |
| 取消协程等于取消退款 | 远端动作可能已经受理，仍需核对 |
| 失败进死信队列就处理完了 | 仍需排查、告警和受控重新投递 |

## 1.8 面试高频问题

### 1.8.1 退款工具超时，如何判断能不能重试？

**参考回答**

先把结果视为未知，不能从超时推断未执行。按稳定操作 ID 查询业务记录；如果服务支持幂等请求，可按原键与原参数有限重试，获取既有结果或继续处理。

若服务既不支持幂等，也没有可靠查询接口，就不能承诺自动重放安全，应通过业务流水核对或转人工。退避和重试次数只控制压力，不解决重复退款。

**面试官追问**

- 查询返回未找到就可以新建吗：还要确认查询的一致性和执行状态，避免读延迟导致误判。
- 用户确实发起另一笔退款怎么办：这是新的业务意图，使用新的操作 ID，但仍需检查剩余可退金额与权限。

**容易答错的地方**

- 把超时、5xx 和明确未执行当成同一种失败。
- 每次重试重新生成业务幂等键。

### 1.8.2 为什么有检查点还需要动作账本和幂等？

**参考回答**

检查点保存程序进度，动作账本记录外部操作的身份与效果。外部服务成功后、本地检查点提交前可能发生崩溃，恢复时相关节点可能再次执行。

因此要用稳定操作 ID 查证或幂等重试，再修复本地进度。仅凭检查点无法保证任意外部服务只产生一次效果。

**面试官追问**

- 把写入单独放成一个节点够不够：有助于清晰划分恢复边界，但仍存在远端成功、本地未记录的窗口。
- 从旧检查点调试有风险吗：有，后续路径可能重新调用真实工具，应该使用模拟实现或隔离环境。

**容易答错的地方**

- 把可恢复执行描述为冻结 Python 调用栈。
- 把框架持久化直接等同于业务恰好一次。

### 1.8.3 如何让持久化任务与消息队列可靠配合？

**参考回答**

先明确任务的持久化事实来源。若任务表与队列是两个系统，可以把任务和 Outbox 事件写进同库事务，再由投递器发送消息，避免任务已创建却丢失调度意图。

投递器与消费者仍可能遇到重复。消费时依据任务状态和业务操作 ID 去重，并在持久记录完成或可靠转交责任后确认消息；持续失败要保留原因并进入可处理队列。

**面试官追问**

- Outbox 为什么还会重复：消息已发送、但发送标记未保存时，恢复会再次投递。
- 简单系统一定要加队列吗：不一定，数据库任务表配合原子领取也可以，选择取决于负载和运维需求。

**容易答错的地方**

- 认为 Outbox 实现了数据库和队列的跨系统事务。
- 消息一到就 ACK，再只用内存保存执行任务。

### 1.8.4 两个 Worker 同时恢复一个任务怎么办？

**参考回答**

用原子领取确定执行者，记录租约和领取代次，提交进度时校验当前执行资格。旧 Worker 即使恢复运行，也不能覆盖新代次状态。

但任务表的检查不能阻止所有外部调用，所以业务动作仍需幂等或下游版本约束。租约解决接管资格，不独自解决外部副作用。

**面试官追问**

- 心跳正常说明任务正常吗：不一定，心跳与业务进度可能分离，还要检查步骤时限和进度更新时间。
- 会话串行就不会重复退款吗：不同会话仍可能访问同一订单，需要业务资源级一致性。

**容易答错的地方**

- 认为超时锁或租约能强制杀死旧执行者。
- 只检查 Worker 名称，不区分同一 Worker 的不同领取代次。

### 1.8.5 用户取消任务后，已经发出的动作如何处理？

**参考回答**

持久记录取消请求，停止派发新步骤，并向运行中步骤传播取消。随后核对已经提交的外部动作，如实保存成功、失败或未知结果。

若业务支持取消或补偿，再按对应协议执行；本地协程停止和浏览器断开都不会自动撤回远端操作。对用户要区分“停止继续执行”与“已发生效果被撤销”。

**面试官追问**

- 任务已经成功，迟到的取消还能改成未执行吗：不能，要依据终态和业务记录说明结果，必要时发起新的补偿流程。
- 补偿失败怎么办：补偿也作为有状态业务操作记录、重试和人工处理，不假定必然成功。

**容易答错的地方**

- 捕获取消异常后直接把所有动作标记为未执行。
- 把补偿描述为不可能失败的数据库回滚。

### 1.8.6 怎样验证恢复机制，而不只证明正常流程能跑？

**参考回答**

沿持久化、消息确认和外部提交边界注入故障，检查重启后任务是否可见、是否继续推进、未知效果是否核对，以及重复尝试是否改变业务结果。

重点测试提交后响应丢失、重复投递、租约过期后旧 Worker 返回、权限变化和取消竞争。观察真实的持久状态与模拟业务效果，而不只检查日志里有没有“恢复成功”。

**面试官追问**

- 关闭连接再打开等于进程崩溃测试吗：不等于，只验证较窄的持久读取与重试路径；进程强杀、并发接管和存储故障需要额外测试。
- 恢复后模型输出不同算失败吗：不必然，判断是否保留用户约束、已发生动作和完成标准；需要复用的决定应事先保存。

**容易答错的地方**

- 只测一次网络超时，就宣称具备生产级恢复能力。
- 用“程序没有报错”代替业务不变量验证。

---

**本章复习收束**

解释一个 Agent 的恢复设计，可以沿这条线展开：任务如何被可靠接收 → 谁拥有执行资格 → 外部动作如何标识 → 哪些窗口可能中断 → 恢复时先核对什么 → 无法确认时怎样收敛。

可靠系统不要求每一步只尝试一次，而要求重复、中断和接管之后，业务效果仍受控，状态仍可信，任务仍有明确去向。

**资料与验证说明**

- 本章围绕应用层任务执行整理，链接用于核对事务发件箱、数据库领取、检查点和 SQLite 接口，不将框架能力等同于端到端保证。
- 已检查标题编号与代码围栏；示例通过语法检查并在 Python 3.9.11 下运行。另行验证了同键重试、参数冲突、非法金额、余额限制，以及业务更新后账本写入失败时的事务回滚。
- 示例仅使用临时数据库和教学数据，不执行真实退款。模拟响应丢失与重开连接，不宣称已经验证进程强杀、并发 Worker 或跨服务恢复。
