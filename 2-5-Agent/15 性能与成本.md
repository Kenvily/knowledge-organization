# 1 性能与成本

Agent 能正确完成任务后，下一个问题是：用户需要等多久，每次任务花费多少，流量增加后是否还能保持效果？

优化不能只看某次模型调用变快了，或输入 Token 变少了。一次任务可能包含多轮生成、检索、工具调用、重试与人工等待，局部节省可能被后续返工抵消。

先抓住一条主线

> 在质量、安全和可靠性约束下，减少不必要的工作，缩短必须完成的路径，并用同一批任务验证收益。

```text
明确任务目标与质量底线
          ↓
记录端到端时间、各步骤耗时与总费用
          ↓
定位：轮次多？输出长？工具慢？排队久？重复计算？
          ↓
选择改动：减工作 / 调整依赖 / 控制并发 / 复用结果
          ↓
对照实验：完成率、尾延迟、每成功任务成本、安全指标
          ↓
通过门槛才上线，并持续观察回归
```

本章聚焦 Agent 应用层。上下文构造与 RAG 原理分别在第 7、8 章，重试与故障恢复在第 14 章；量化、GPU 显存和推理服务调度留给 AI Infra 专题。

## 1.1 先定义衡量标准

### 1.1.1 首 Token、有效反馈与完成时间

不同延迟指标回答不同问题，不能只用一个“响应时间”概括。

| 指标 | 起止边界示例 | 反映什么 |
| --- | --- | --- |
| 首 Token 延迟，TTFT | 一次模型请求发出，到首个输出 Token 到达 | 该次生成开始得快不快 |
| 首次有用反馈时间 | 用户提交，到首次可验证的进度或结果展示 | 用户多久得到有价值的信息 |
| 任务完成时间 | 用户提交，到符合验收条件的结果交付 | 用户真正等了多久 |
| 系统处理时间 | 排除明确记录的人工等待，保留系统执行和排队 | 系统自身效率 |

如果平台把 TTFT 定义为“用户提交到首个可见 Token”，它会包含请求前处理等时间。必须记录实际起止点，不把不同平台同名指标直接比较。

订单案例中，0.2 秒显示“正在处理”，3 秒显示已查到的订单状态，8 秒交付带政策依据的判断。这三个时刻不同：固定提示可改善交互感受，但不能冒充已取得业务进展。

流式展示可以提前暴露已有结果，不必等待完整文本生成；它不自动减少总计算量，也不保证最终完成更快。需要审批的任务还应分别记录系统处理和等待人的时间，避免把用户离开几小时归因为模型慢。

### 1.1.2 平均值、分位数与失败请求

平均延迟适合看总体趋势，但可能掩盖少数非常慢的任务。p50、p95、p99 分别描述延迟分布的相应百分位，常用来观察典型体验和尾部体验。

例如，同类任务大多数 3 秒完成，少部分因重试超过 30 秒。只优化正常调用可能降低平均值，却无法改善最慢的一批用户。

统计时至少明确：

- 任务类型、样本量和时间窗口；少量样本的 p99 不稳定。
- 成功、失败、超时和取消分别有多少，不能静默丢掉慢失败。
- 超时记录代表达到等待上限，不代表任务真实完成时间。
- 多实例汇总应合并样本或合适的分布统计，不能简单平均各实例的 p95。

快速返回错误会让“平均响应时间”变好，但服务能力并没有改善。应同时观察成功请求、失败请求的延迟及错误率。[Google SRE 的监控讨论](https://sre.google/sre-book/monitoring-distributed-systems/)

### 1.1.3 每任务成本与每成功任务成本

一次任务的模型费用应汇总所有模型调用，包括重试、路由、摘要、评审、子 Agent 和最终汇总，而不只看最后回答。

```text
任务成本
  = 所有模型调用费用
  + 检索、重排和工具服务费用
  + 按口径分摊的执行、存储与观测费用
```

模型费用常由未缓存输入、缓存读取或写入、输出等计费项组成。不同服务的字段、最低计费单位和附加费用不同，应按用量记录及实际合同计算，不能假定“所有 Token 同价”。

如果报告只统计 API 直接费用，就标明这一范围；不要把它称为包含人工审核和自建基础设施的总成本。自托管模型同样有设备、运行和运维成本，不是 API 账单为零就免费。

一个重要指标是：

```text
每成功任务成本 = 同一批任务的总成本 / 其中成功完成的任务数
```

假设同样 100 个任务，方案 A 总成本 400 个教学费用单位，完成 80 个；方案 B 花费 360，完成 60 个。单任务平均成本由 4 降到 3.6，但每成功任务成本由 5 升到 6。

这说明更便宜的调用可能因为失败和返工，导致更贵的有效交付。这个指标是批次层面的成本分摊，不表示每个具体成功任务实际花费相同；成功数为零时不能报告为零成本。

### 1.1.4 并发、吞吐与服务目标

并发是同时处理多少工作，吞吐是单位时间完成多少工作，延迟是单个任务经历多久。增加并发不等于三者同时改善。

当服务还有空闲能力时，并发可以提高利用率；接近瓶颈后，增加并发可能主要增加排队、超时与重试，使尾延迟和成功吞吐恶化。

Agent 还要区分任务吞吐与内部请求吞吐：一个任务平均调用模型 5 次，10 个任务/秒可能意味着约 50 次模型请求/秒，未计失败重试。只按入口请求数量申请资源会低估下游压力。

优化前先设任务级目标，例如“正常订单查询需要在可接受时间内完成，且准确率、越权率不退化”。目标应按业务确定，不把某个固定秒数当作所有 Agent 通用标准。

## 1.2 沿执行轨迹定位瓶颈

### 1.2.1 时间相加与关键路径

串行步骤的时间大致相加；独立步骤并行后，合流时间取决于最慢分支及额外开销。关键路径指决定任务何时能完成的依赖路径。

下面全部是教学耗时，不是模型或框架性能承诺：

```text
串行：规划 1 秒 → 查订单 2 秒 → 查通用政策 3 秒 → 汇总 2 秒
总时间约 8 秒

并行：规划 1 秒 → ┬─ 查订单 2 秒 ───┐ → 汇总 2 秒
                 └─ 查通用政策 3 秒 ─┘
总时间约 6 秒，尚未计额外调度和排队开销
```

如果政策必须依据订单购买日期筛选，两步就有依赖，不能直接按此并行。是否并行首先是正确性问题，其次才是性能问题。

各步骤的累计耗时可以大于任务墙钟时间，因为它们可能重叠。不能把所有子调用时间直接加起来，再宣称用户实际等了这么久；同样，任务 p95 也不能通过各阶段 p95 相加得到。

### 1.2.2 Trace 应记录什么

Trace 表示一次任务的执行轨迹，Span 表示其中一个操作区间。这里先使用它们定位时间与费用，第 16 章再展开完整观测体系。

建议记录：

- 任务、步骤、父子调用与尝试 ID，便于识别重试和子 Agent。
- 开始、结束、状态，区分排队、实际调用和退避等待。
- 模型、提示词和工具版本，以及输入输出用量。
- 缓存命中类型、候选文档数量、重排数量和结果体积。
- 错误、超时、取消，以及是否真的满足任务验收条件。

测单进程耗时宜使用单调时钟，例如 Python 的 `time.perf_counter()`，避免系统时间校准影响时间差。跨服务则需要一致的追踪关联，不能直接相减两台机器未同步的时间戳。

费用汇总要防止重复记账：如果 SDK 和工具包装层都报告同一次模型调用，应使用调用标识对应，而不是将两个记录都当成额外调用。

### 1.2.3 按症状选择第一步改动

| 观察到的现象 | 优先调查 | 不应直接下的结论 |
| --- | --- | --- |
| 每次模型调用不慢，总任务却慢 | 轮次、串行依赖、重复检索与重试 | 一定要换更快模型 |
| 负载上升后尾延迟突增 | 队列、连接池、限流和依赖容量 | 只需无限增加 Worker |
| Token 很多但有效证据少 | 工具输出、历史增长、重复内容 | 把上下文直接截短即可 |
| 输入减少但费用没有下降 | 输出、缓存写入、评审和额外轮次 | 用量统计一定出错 |
| 平均值变好，复杂任务明显变差 | 路由误分、长任务裁剪和失败样本 | 总平均值达标即可上线 |

优先改占比高且可避免的工作。如果 90% 时间花在外部慢工具上，把本地消息转换提速两倍，对整体影响仍然有限。

## 1.3 减少不必要的模型与工具工作

### 1.3.1 先减少无效轮次

多一轮模型调用，往往不只增加一次生成，还要重新发送历史、工具说明和新结果。因此减少无效往返经常比微调一次调用更有价值。

常见做法包括：

- 固定业务规则交给程序判断，不让模型反复确认已知分支。
- 工具返回足够决策的必要字段，避免“查订单后再查同一订单购买时间”。
- 澄清时一次询问当前确实需要的缺失项，不拆成很多孤立追问。
- 完成条件已满足就交付，不为每个简单任务固定增加规划、反思和多专家评审。

但合并工具不能破坏业务边界。为了省一轮，把“查询资格”和“直接退款”强行合成工具，可能失去独立审批机会；这里仍应遵守第 2、13 章的动作与权限设计。

提前退出应依赖明确条件，例如必要字段齐全、证据足以支持结论、用户未要求进一步动作。没有检查覆盖就提前生成短答案，不属于有效优化。

### 1.3.2 控制上下文与输出长度

先删重复和无关信息，再考虑摘要或检索裁剪。关键目标、有效约束、批准参数、工具消息关系和决定结论的证据不能静默删除。

| 改动 | 可能节省什么 | 必须检查什么 |
| --- | --- | --- |
| 工具结果只回必要字段，长结果改引用 | 输入和历史重复传输 | 是否丢失分页、例外、来源与完整性标记 |
| 旧历史摘要与结构化进度 | 后续每轮输入 | 摘要是否把推断变事实，是否遗漏约束 |
| 检索去重、调整候选与重排数量 | 检索、重排和模型输入 | 关键证据召回率是否下降 |
| 最终结果按所需字段输出 | 输出 Token 与后处理 | 是否足够表达结论、依据和缺失项 |

输出通常是逐步生成的，减少不必要的长篇输出可能降低生成时间和费用；实际收益仍取决于模型、服务和任务。调低最大输出上限不等于提高生成速度，也可能让 JSON 或关键解释被截断。

摘要本身也消耗模型调用。一次性短任务里先花一轮做摘要，未必划算；较长、多轮复用的任务才更可能摊薄这笔开销。比较时应计入摘要生成和失真后的补查成本。

### 1.3.3 模型分级路由与升级策略

模型路由是把适合的任务交给满足要求的模型，而不是一律使用最便宜或最强的模型。例如规则清晰的分类、字段提取与复杂跨文档推断，可以分别评估。

```text
任务特征与风险
      ↓
规则可确定 → 程序处理
常规任务   → 较低成本模型 → 结果验证
                              ├─ 达标 → 交付
                              └─ 未达标 → 升级模型或转人工
复杂任务   → 直接使用经验证更适合的模型
```

验证条件应尽量来自真实证据：Schema、业务规则、必要信息覆盖与独立测试结果，而不只依据模型自报“置信度 0.99”。自评分数未经校准，不应当成可靠成功概率。

假设低成本路径费用为 Cs，有比例 q 的任务升级，高成本路径费用为 Cl，验证费用为 Cv，则简化期望费用为：

```text
级联平均费用 ≈ Cs + Cv + q × Cl
```

若 q 很高，先尝试便宜模型再升级可能比直接使用高成本模型更贵、更慢。这个估算还未包含重试和复杂提示增长，应以真实调用链修正。

升级模型也不能自动解决缺数据、无权限或错误工具结果。路由要检查工具调用和结构化输出兼容性，并在不同任务难度上分别验证成功率。

## 1.4 缩短关键路径并控制并发

### 1.4.1 独立步骤并行，而不是所有步骤并发

并行适用于没有数据依赖、没有冲突副作用的工作。只把原来串行的三个调用同时启动，一般不减少总调用数量；它主要减少可重叠的等待时间。

如果多个专家重复搜索同一资料，还额外引入主管和汇总，可能延迟更低但成本更高。应分别统计墙钟时间与全部分支费用。

并行还有尾部效应：必须等所有结果才能汇总时，最慢分支决定合流时间。可以根据任务要求设置分支超时或接受部分结果，但不能丢掉必要证据后仍标记完整成功。

“向多个服务发相同请求，谁快用谁”的冗余请求策略会增加工作量和潜在计费，对写入更可能造成重复效果；不是默认并行方案，应明确只读或幂等条件及容量预算。

### 1.4.2 异步、连接复用与并发上限

异步 I/O 让等待网络的任务把执行机会交给其他任务，减少线程或事件循环的空等；它不会把一个本来需要 2 秒的远端服务变成 1 秒。

在异步函数中直接执行阻塞调用，仍可能卡住事件循环。CPU 密集计算也不能只靠增加协程获得多核加速，需要按运行环境选择进程、线程或外部计算服务。

HTTP 客户端的连接池可以复用已有连接，减少反复连接建立等开销。客户端宜在合适生命周期内复用，并配置连接数量、超时及关闭逻辑，而不是每次工具请求都创建和销毁一个客户端。[HTTPX 客户端与连接复用](https://www.python-httpx.org/advanced/clients/)

并发上限应结合模型请求额度、Token 额度、工具容量和任务风险设置。单个进程的 Semaphore 只限制该进程内的工作；多个 Worker 各限制为 10，不等于全系统限制为 10。

### 1.4.3 排队与预算也是性能设计

连接池、Worker 和外部配额都可能成为排队点。只测服务端执行耗时，而不测排队时间，会误把容量问题当作偶发网络慢。

预算应限制整项任务的轮次、模型用量、工具次数、分支数量和截止时间。并行派发时可先预留预算，再按实际使用结算，避免各分支同时看见同一份剩余额度并超支。

预留是估算，不是对最终账单的绝对保证；已发出的调用被取消后，仍可能产生服务端计算与费用。账单应以提供商用量和实际完成情况核对。

减小超时可能让慢请求更快失败，却不一定让任务更快完成；如果失败后重试或升级模型，最终成本反而可能增加。超时与恢复语义应沿用第 14 章，不为追求延迟指标牺牲真实完成率。

## 1.5 缓存复用与失效边界

### 1.5.1 先分清缓存的对象

不同缓存跳过的工作不同，不能把所有命中都叫作“直接复用答案”。

| 缓存对象 | 复用什么 | 仍需处理什么 |
| --- | --- | --- |
| 文档解析、Embedding | 同版本资料的处理结果 | 更新、删除和索引一致性 |
| 检索结果 | 查询范围内的候选片段 | 权限、资料版本与新鲜度 |
| 只读工具结果 | 相同请求下仍有效的数据 | 动态状态变化和可接受陈旧程度 |
| 最终回答 | 已验证且条件一致的产物 | 身份、上下文、证据和任务条件是否等价 |
| 模型输入前缀缓存 | 部分重复输入的处理结果 | 本轮新内容的处理与输出生成 |

前缀缓存不是答案缓存，通常仍然会调用模型生成输出。以提供商的 Prompt Caching 为例，命中条件、支持范围、有效期和读写计费由具体服务定义，不能套用固定折扣或认为写入免费。[Prompt Caching 官方说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

稳定规则与工具说明放在可复用的输入部分可能有利于前缀命中，但不能为了命中保留过期身份、错误状态，或忽略服务的具体匹配方式。

### 1.5.2 缓存键表达语义依赖

缓存键应包含所有会改变可见结果的依赖，但不同缓存不必机械使用完全相同字段。

```text
检索结果键示意
  租户 / 访问范围
  + 规范化查询与筛选条件
  + 语料和索引版本
  + 检索配置版本
```

文档的公共解析结果可能按内容版本共享；用户私有查询结果则不能只按问题文本共享。参数顺序等无关差异可以规范化，但不能把时间、金额或业务限定词删掉，以至于两个不同问题变成同一键。

最终答案更难缓存，因为相同问题可能对应不同订单状态、权限、历史约束或政策版本。语义缓存按相似性匹配，命中范围更宽，也更容易误用“看起来相近但条件不同”的结果，需要额外验证。

### 1.5.3 新鲜度、击穿与净收益

TTL（有效期）只限制缓存多久后过期，不保证期间数据没有变化。实时订单与付款状态对陈旧程度要求更高；执行退款前，应在业务服务中重新验证，不能依赖昨天的查询缓存。

缓存维护还要考虑：

- 资料或权限变化时，失效、版本切换或访问时复核如何生效。
- 大量请求同时未命中时，是否会重复回源；可合并同键的并发读取，但只在访问范围兼容时共享。
- 大量键同时过期时，是否造成突发流量；可以错开过期或受控刷新。
- 缓存不可用时，是否允许回源；下游没有容量时不能无限回源。

缓存不是免费优化。应比较命中带来的节省与查询、写入、存储、刷新、失效维护成本，同时计入错误命中的质量风险。

短任务、低复用资料、频繁变化的查询可能收益有限。报告命中率时还应区分“请求命中比例”和“实际节省的 Token 或计算量”，不能认为命中 80% 就一定省掉 80% 成本。

## 1.6 对照实验与可运行示例

### 1.6.1 用一份实验表同时看收益与代价

优化前先保存基线：固定任务集、输入资料与版本、模型配置、工具环境、负载方式和计费口径。尽量一次验证一类主要改动，再测试组合效果。

下面是实验记录模板，不是真实跑分：

| 方案 | 主要假设 | 必测收益 | 关键风险 |
| --- | --- | --- | --- |
| 基线 | 当前实现作为比较对象 | 完成率、p50/p95、总成本 | 样本是否代表真实任务 |
| 减少固定评审轮 | 简单任务不需要额外模型检查 | 调用次数、任务成本 | 难任务或高风险错误漏检 |
| 独立查询并行 | 等待可以重叠 | 端到端与排队时间 | 限流、错误传播和依赖判断 |
| 上下文压缩 | 去掉重复历史 | 输入用量、后续轮次 | 早期约束丢失与补查增加 |
| 模型级联 | 常规任务可走低成本路径 | 每成功任务成本 | 升级率、误分和尾延迟 |
| 增加缓存 | 存在重复且有效的数据 | 冷热缓存下的净收益 | 陈旧数据、权限和维护成本 |

冷缓存、热缓存要分别测，并说明真实流量中两者比例。不能先让新方案预热、旧方案全部冷启动，再把差距归因为算法改进。

对不同任务难度、文档长度、租户和成功/失败类型分别分析。随机化或交替运行方案有助于减少时段差异；模型输出有波动时需要重复采样，不能只挑一次最快结果。

### 1.6.2 标准库示例：并行减少等待，不减少调用量

以下 Python 3.9+ 示例用异步等待模拟四个独立只读工具。用并发上限 1 和 2 对比相同工作，记录耗时、调用次数、峰值并发和教学费用单位。

不调用模型、不联网、不产生真实费用。这里的等待时间只是实验设置，不代表任何服务性能。

```python
import asyncio
from dataclasses import dataclass
from time import perf_counter


@dataclass
class Stats:
    calls: int = 0
    active: int = 0
    peak: int = 0
    cost_units: int = 0


async def run_case(limit):
    if type(limit) is not int or limit <= 0:
        raise ValueError("limit must be a positive integer")
    semaphore = asyncio.Semaphore(limit)
    stats = Stats()

    async def read_tool(item):
        async with semaphore:
            stats.calls += 1
            stats.cost_units += 3  # 教学计费：每个调用固定 3 单位。
            stats.active += 1
            stats.peak = max(stats.peak, stats.active)
            try:
                await asyncio.sleep(0.03)  # 模拟可重叠的 I/O 等待。
                return {"item": item, "ok": True}
            finally:
                stats.active -= 1

    started = perf_counter()
    results = await asyncio.gather(*(read_tool(i) for i in range(4)))
    elapsed = perf_counter() - started
    assert stats.active == 0
    return results, stats, elapsed


async def main():
    serial_result, serial_stats, serial_time = await run_case(1)
    parallel_result, parallel_stats, parallel_time = await run_case(2)
    assert serial_result == parallel_result
    assert serial_stats.calls == parallel_stats.calls == 4
    assert serial_stats.cost_units == parallel_stats.cost_units == 12
    assert serial_stats.peak == 1
    assert parallel_stats.peak == 2
    for name, stats, elapsed in [
        ("limit=1", serial_stats, serial_time),
        ("limit=2", parallel_stats, parallel_time),
    ]:
        print(name, "seconds=", round(elapsed, 4),
              "calls=", stats.calls, "peak=", stats.peak,
              "cost_units=", stats.cost_units)


if __name__ == "__main__":
    asyncio.run(main())
```

在无明显额外干扰时，两组等待分别接近 0.12 秒和 0.06 秒，但实际值由运行环境决定。代码不把固定加速倍数写成断言，因为计时会受调度和系统负载影响。

### 1.6.3 关键语句与验证边界

按执行顺序理解：

1. `Semaphore(limit)` 限制实际进入工具体的协程数量；在等待许可时，不计入本例的活跃工具数。
2. `calls` 和 `cost_units` 在执行开始时增加，刻意将调用工作量与墙钟时间分开。
3. `asyncio.sleep()` 让出执行机会，模拟 I/O 等待；换成阻塞调用就不能假定仍有相同并发效果。
4. `finally` 确保执行结束或取消时递减活跃计数，但不代表远程工具也已被取消。
5. `gather` 并发等待所有协程，并按输入顺序返回结果；本例是全部成功的路径，不实现完整分支失败策略。[Python 异步任务说明](https://docs.python.org/3/library/asyncio-task.html)
6. `perf_counter()` 测量整个案例的实际时间；结果断言检查工作内容、调用次数与并发边界，而不承诺固定耗时。

这个示例证明的是：在可重叠等待的教学模型里，可以让同样的工作并发执行，且调用数量和设定费用保持不变。它不是模型服务压测，也没有覆盖网络连接池、速率配额、分布式限流或生产重试。

真实接入时还要设置单次与任务级期限、异常传播和取消规则。不要因为 `gather` 已经返回异常，就默认所有其他外部动作都停止了。

### 1.6.4 以质量门槛决定是否上线

上线条件不能只有“更快”。先设不可接受的回归，例如越权、证据缺失却给出确定结论、必要审批被跳过；再检查任务成功率、延迟和成本是否满足目标。

如果两个方案各有优劣，可以按任务类型选择，不必强行给出全局唯一赢家。一个方案若在所有关心的指标上都不更好，就没有明显采用理由；存在真实取舍时，应由业务权重和风险约束决定。

上线宜先小范围观察，并保留回退能力。回归集用于持续比较，不应只靠反复调同一批测试题获得漂亮数字；还需要未参与调优的样本和真实反馈。

## 1.7 常见误区

| 误区 | 正确认识 |
| --- | --- |
| 首 Token 快就代表任务快 | 还要看有效反馈和完整任务交付时间 |
| 并行会同时降低费用 | 相同工作并行通常不减少总调用量 |
| async 能让任何函数变快 | 主要帮助重叠等待，阻塞或 CPU 工作仍需正确处理 |
| 并发越大吞吐越高 | 超过下游容量后可能增加排队和失败 |
| 输入 Token 下降就说明总成本下降 | 还可能增加摘要、输出、升级或补查费用 |
| 最便宜模型一定最省 | 失败、重试与升级可能提高每成功任务成本 |
| 缓存命中就能直接返回答案 | 要区分缓存对象，并检查权限与有效条件 |
| TTL 能保证实时正确 | 有效期内数据仍可能变化 |
| p95 可以跨阶段或实例直接相加、平均 | 分位数需要对应原始分布或可合并统计 |
| 把慢任务快速拒绝就是优化成功 | 仍需检查完成率与失败分布 |

## 1.8 面试高频问题

### 1.8.1 一个 Agent 很慢，你会怎样定位？

**参考回答**

先定义慢的是首 Token、首次有效反馈还是完整任务，再按任务轨迹拆解排队、模型、检索、工具、重试和人工等待。观察平均值与尾延迟，按任务类型和成功失败分组。

然后找决定完成时间的关键路径和重复工作。轮次过多先减无效往返，工具等待长先看依赖与连接，负载下变慢则重点检查容量和排队，不一开始就换模型。

**面试官追问**

- 各步骤耗时加起来为什么比总耗时大：步骤可能并行重叠，累计工作时间不等于墙钟时间。
- 为什么不能只看平均值：重试和排队可能集中影响少数任务，需要分位数与错误分布解释。

**容易答错的地方**

- 没有测量就断定是模型推理慢。
- 把固定“正在处理”提示当作有效结果，掩盖真实等待。

### 1.8.2 并行和异步分别解决什么问题？

**参考回答**

并行设计让没有依赖的工作重叠，缩短关键路径；异步 I/O 是实现等待重叠的一种方式，不会降低远端操作自身所需时间。

还要限制并发，避免打满模型或工具容量。同样四次调用从串行改并发，工作量未必下降，所以时间改善不能直接推出费用下降。

**面试官追问**

- 所有查询都能并行吗：不一定，例如政策范围依赖订单日期，必须先取得日期或采用明确正确的替代流程。
- 并发越高为什么 p95 越差：资源争用、下游限流与排队增加，重试还可能进一步放大压力。

**容易答错的地方**

- 在 async 函数里使用阻塞调用，却认为自动获得异步执行。
- 把单进程的并发上限当成全系统限流。

### 1.8.3 如何降低成本而不明显损害任务效果？

**参考回答**

先减少确定不必要的工作，例如重复查询、无效规划评审、冗长工具结果和无用输出；再评估上下文压缩、结果缓存与模型路由。必要证据、约束和审批不能为了省 Token 删除。

衡量时汇总全部调用和失败费用，比较任务成功率与每成功任务成本，而不只看模型单价或单次输入长度。

**面试官追问**

- 为什么用小模型反而更贵：可能更容易误选工具、增加轮次，或者频繁升级到更贵模型。
- 摘要一定省钱吗：要计入摘要生成、复用次数和遗漏造成的补查，短任务可能不划算。

**容易答错的地方**

- 只展示 Token 减少比例，不检查是否返工。
- 成功任务减少却依然宣称降本有效。

### 1.8.4 前缀缓存、工具缓存和答案缓存有什么区别？

**参考回答**

前缀缓存复用部分重复输入的处理，通常仍需模型生成；工具缓存复用某次读取结果；答案缓存直接复用最终产物，对上下文等价性要求更高。

设计时明确缓存键、版本、权限范围和新鲜度。相同问题文本不代表相同用户、订单状态和政策条件；缓存命中不能绕过授权。

**面试官追问**

- 实时订单适合长期缓存吗：通常要按可接受陈旧程度限制，并在执行关键动作前重新核验业务条件。
- 为什么缓存命中率高但收益不大：可能命中的都是小对象，或读写维护费用抵消收益，应测实际节省的工作和净成本。

**容易答错的地方**

- 把缓存输入等同于不调用模型。
- 只用查询字符串作为所有用户共享的缓存键。

### 1.8.5 怎样判断模型级联是否值得？

**参考回答**

统计低成本路径的成功率、升级率、验证费用和升级后的总耗时。简化费用是低成本调用加验证，再加升级概率乘高成本调用费用；升级比例高时，级联可能不如直接使用合适模型。

路由依据应在代表性任务上验证，结果检查不能只信模型自报置信度。对缺数据或权限不足的任务，升级模型也不能自动补齐前提。

**面试官追问**

- 是否应该所有任务先走最便宜模型：不一定，已知复杂或高风险任务可以直接走经过验证的路径，避免付出两次调用成本。
- 路由器自身算不算成本：算，还应计入它带来的等待、误分和维护成本。

**容易答错的地方**

- 忽略升级路径叠加的费用与尾延迟。
- 用未经校准的自评分数作为唯一升级条件。

### 1.8.6 怎样证明一次优化真正有效？

**参考回答**

在可比较的任务、负载和版本条件下建立基线与新方案，分组记录成功率、错误、延迟分布、总成本及每成功任务成本。缓存冷热、失败重试和子 Agent 费用都要纳入口径。

先守住安全与质量门槛，再比较性能收益；用重复测试和未参与调优的样本降低偶然性，逐步上线并观察回归。

**面试官追问**

- 只跑一次最快结果够吗：不够，调度、模型生成和服务负载都有波动，应报告样本与分布。
- 平均成本下降但复杂任务失败更多怎么办：分难度分析，可能仅对简单任务启用，不能用平均值掩盖关键场景退化。

**容易答错的地方**

- 用不同模型版本、不同缓存状态或不同任务集比较，却不说明差异。
- 把示意代码的等待加速比例当成真实模型服务跑分。

介绍一次优化时，按“原始瓶颈 → 测量证据 → 为什么选这项改动 → 时间和费用如何变化 → 质量与安全是否保持 → 适用范围”说明。

性能优化的核心不是把每个组件都变快，而是在既定约束下少做无效工作、让必要工作更合理地执行，并证明整体交付确实改善。
